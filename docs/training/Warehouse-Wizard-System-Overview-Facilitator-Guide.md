# Warehouse Wizard System Overview — Facilitator Guide

**Length:** 45 minutes  
**Audience:** client key persons, managers, supervisors, clerks, and operator representatives  
**Product baseline:** Warehouse Wizard 1.27

## Purpose

This session explains what every current module does, who normally uses it, the normal action taken there, and where the work goes next. It complements the 60-minute end-to-end workflow presentation; it does not replace hands-on role competency.

The audience’s warehouse experience is the foundation. Present the system as a way to keep the team’s existing knowledge visible between people, shifts, and facilities—not as a lesson on how warehouses ought to operate.

Use this rhythm throughout:

1. Ask how the team handles the situation now.
2. Name the physical fact they already check.
3. Show where Warehouse Wizard records that fact.
4. Explain who can see the handoff next.
5. Ask what real exception they would expect on their floor.

## Teaching pattern for every module

Use the same five questions:

1. What business purpose does this module serve?
2. Which role normally owns it?
3. What is the normal action sequence?
4. What module or person receives the handoff?
5. What mistake should stop the user?

## Suggested module-selection exercise

Ask the room to name the correct module:

- A pallet is moving to another bay in the same warehouse → **Location Moves**.
- A pallet is moving to another facility → **Transfers**.
- A printed pallet code is unreadable → verify in **Inventory Search**, then reprint the same identity.
- A pick pallet is physically short → stop, use **Inventory Search**, a justified controlled **Status**, and **System Log** ownership.
- A new SKU has no pack barcode → **Products** and **Packaging Profiles** before Receiving.
- The receiving form and pallet were left during a disconnect → reconnect, refresh **Receiving**, verify live state, then post once.
- A manager sees rising quarantine stock → open **Reports/Dashboard**, then drill into **Statuses**, Inventory Search, and accountable logs.

## Close

Remind participants that a module is not a silo. Normal work finishes with a clear handoff, and exceptions return to live verification before another transaction is released.
