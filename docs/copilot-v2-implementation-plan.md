# Task: Build Copilot v2 — one shared tool registry, many surfaces

You are working in the **Warehouse Wizard** repo (Vite + React + TypeScript, Supabase Auth + Postgres RLS + Deno edge functions). This is an implementation brief for `.lovable/plan/copilot-v2-one-tool-layer-many-surfaces-2026-08-13.md`. Read that plan doc first — it has the full rationale. This brief turns it into ordered, independently-shippable phases. Do **not** do everything at once — each phase should ship, get verified, and get reported on before the next starts.

---

## Context: how copilot works today (verified against the code, 2026-08-18)

- **In-app copilot:** `supabase/functions/copilot/index.ts` exposes exactly 9 read-only tools via a flat `toolDefs` array + a single `switch(name)` in `runTool()`, run in a step loop (`MAX_STEPS=5`) against the Lovable AI gateway (`google/gemini-3.6-flash`). Auth: a Supabase client built from the publishable key + the caller's Bearer JWT (RLS-scoped), identity verified via `sb.auth.getClaims(token)`. A **separate service-role client** exists only to write `copilot_tool_calls` audit rows — it's never used for tool execution. Role/warehouse scope is resolved via a `profiles` table lookup per request, **not** JWT claims.
- **MCP server:** source at `src/lib/mcp/index.ts` + `src/lib/mcp/tools/{list-warehouses,search-products,inventory-summary,_supabase}.ts`; deployed as `supabase/functions/mcp/index.ts`, auto-generated by `@lovable.dev/mcp-js`. Exposes exactly 3 tools. OAuth issuer points at Supabase Auth; each tool builds a per-request client from the caller's token — RLS-scoped, no service role.
- **Chat UI:** `src/features/copilot/copilot-panel.tsx` + `copilot-core.ts`. Text only — no voice, no attachments today.
- **Roles:** real DB enum `public.app_role_code` = `admin, warehouse_manager, inventory_clerk, warehouse_operator, dispatch_driver, dev, developer, warehouse_supervisor`, enforced via `has_min_role()` in RLS (see `supabase/migrations/20260511000000_consolidated_wms_schema.sql` and later `ALTER TYPE` migrations). `COPILOT_ACCESS_ROLES` in `src/hooks/use-feature-flags.ts` currently = `developer, admin, warehouse_manager, warehouse_supervisor`.
- **Feature flags:** two separate, unrelated client-side mechanisms — `use-feature-flags.ts`'s per-user `localStorage` `ModuleKey: "copilot"` toggle, and `copilot-core.ts`'s `isCopilotPreviewHost()` (hides the panel on production hostnames unless a separate `localStorage` override key is set). Neither is server-controlled.
- **Audit schema already exists** (migration `20260806032746_...sql`): `copilot_conversations`, `copilot_messages`, `copilot_tool_calls`, and an unused generic `copilot_suggestions` (`surface text, suggestion jsonb, decision: pending|accepted|rejected`). All RLS-scoped to `user_id = auth.uid()`.
- **`container-vision`** (`supabase/functions/container-vision/index.ts`): single JPEG in, single ISO 6346 container code out, locally re-validated against the check-digit algorithm. Narrow and single-purpose.
- **`reports-core.ts`** (`src/features/reports/`): existing CSV import pipeline — `importCsvToResource()`, `previewImport()`/`commitImportRows()`, generic over a `ResourceDefinition.table`, archives source files to the `imports` storage bucket.
- **`/reports`** route → `ReportsPage` (defined in `src/features/status/status-page.tsx`) already exists and is a real target for a future "Open in Reports" directive.
- **Sharing precedent:** `supabase/functions/_shared/` already exists (`netsuite.ts`, email templates) as the pattern for code shared between Deno edge functions. Nothing in `supabase/functions/` imports from `src/` today.

## Decisions locked in design review (2026-08-18)

Full rationale in the plan doc's "Resolved in design review" section. Binding for this implementation:

1. Registry lives at `supabase/functions/_shared/copilot-tools/` — **not** `src/lib/copilot-tools/`.
2. Draft-producing tools get bespoke tables per capability (`copilot_import_drafts`, `copilot_import_mappings`, `copilot_approvals`) — do not repurpose the existing unused `copilot_suggestions` table.
3. `ingest_document` is new code (`supabase/functions/copilot-ingest/`) sharing only the AI-gateway call pattern with `container-vision` — not a literal call into it. `container-vision` is untouched.
4. The chat-driven import tools are new, independent logic in the registry — do not build them on top of `reports-core.ts`.
5. Voice ships push-to-talk + optional TTS only in its phase. Hands-free/wake-word mode is explicitly out of scope until a later, separately-scoped phase.
6. MCP stays read-only for v1 — the MCP adapter filters the registry to `kind: "read"` only. Draft and `ui` tools are in-app chat panel only.
7. A new server-side capability flag (per-warehouse/per-role) gates each new capability as it ships. It's additional to, not a replacement for, the existing `COPILOT_ACCESS_ROLES` role gate and `isCopilotPreviewHost()` mechanisms.
8. Copilot access itself stays a personal, per-user opt-in at every role level (`ModuleKey: "copilot"`) — unaffected by the new capability flag. A capability being enabled for a role/warehouse never turns copilot on for a user who hasn't opted in themselves.

## Hard constraints (read `AGENTS.md` first)

- `supabase/migrations/**` — **additive only.** Never edit an existing migration file; create a new timestamped file per change.
- `supabase/config.toml` — function-specific blocks only; project-level settings need explicit user approval.
- `src/integrations/supabase/client.ts` and `types.ts` — auto-generated, never hand-edit. Regenerate types via the Supabase CLI/MCP after every schema change.
- `src/lib/wms-core.ts`, `src/lib/enterprise-wms.ts`, `src/lib/help-content.ts` — edit freely; keep exported shapes stable unless a phase requires a coordinated update.
- No model-generated SQL, ever. Tools call typed handlers only.
- Every tool call, suggestion, acceptance, and rejection stays audited — extend `copilot_tool_calls`, never bypass it.
- Run `bunx tsc --noEmit` (or the harness build) and the relevant tests before declaring any phase done.
- Per AGENTS.md §1: UI is not frozen, but keep each phase's visible changes scoped to what that phase's capability needs — no incidental redesign.

## Phase 0 — Capability flag + registry skeleton (no user-visible behavior change)

Goal: every later phase has a flag to ship behind, and the existing 9+3 tools move onto the shared registry with zero behavior change.

1. **Additive migration:** `copilot_capability_flags(id uuid pk, capability text, role public.app_role_code null, warehouse_id uuid null references warehouses(id), enabled boolean not null default false, created_by uuid, created_at timestamptz default now())`. Null `role`/`warehouse_id` means "applies to all." RLS: readable by `authenticated`, writable by `admin`/`developer` only.
2. **Scaffold `supabase/functions/_shared/copilot-tools/`:** one file per tool. Port the existing 9 read tools out of `copilot/index.ts`'s switch statement and the 3 MCP tools out of `src/lib/mcp/tools/*`, each as `{ name, description, inputSchema (Zod), kind: "read", minRole, handler(input, ctx) }`. `ctx = { supabase, userId, roles, warehouseId }`, resolved the same way `copilot/index.ts` already resolves it today (a `profiles` lookup, not JWT claims) — do not change that resolution logic, just relocate it into the registry's context builder.
3. **Registry module:** filters the tool catalog per caller by `minRole` and by the new capability flag (default-enabled for these 12 existing tools so nothing regresses); re-checks both server-side at execution time.
4. **Rewire `supabase/functions/copilot/index.ts`** to build its tool defs and dispatch from the registry instead of the local switch. This phase must not change observable behavior.
5. **Rewire `src/lib/mcp/index.ts`** + its 3 tool files to wrap the same registry entries in `defineTool` (`kind: "read"` only). Regenerate the MCP manifest (`.lovable/mcp/manifest.json`).

**Acceptance:** `tsc --noEmit` clean. All 9 in-app tools and all 3 MCP tools behave identically to before this phase (exercise each manually). `copilot_capability_flags` exists with RLS but nothing outside the registry's filter reads it yet.

## Phase 1 — UI directives (`ui` tool kind)

1. Add `open_module`, `open_record`, `start_workflow` to the registry (`kind: "ui"`), returning `{ action: "navigate", route, params, label }`. Never auto-navigate.
2. New `src/features/copilot/directives.tsx`: renders returned directives as buttons in the chat panel; click navigates via `react-router`.
3. MCP adapter already filters to `kind: "read"` from Phase 0 — confirm `ui` tools don't leak into its catalog.
4. Gate behind the capability flag (default off; enable per warehouse/role once verified in review).

**Acceptance:** asking the copilot to open a module/record renders a button that navigates only on click, never automatically. MCP catalog unchanged. `tsc` + tests green.

## Phase 2 — Reporting (`run_report`)

1. Server-side report registry: stock on hand, expiring stock, receiving throughput, pick productivity, adjustments, movement history, empty/over-capacity locations — each with a typed param schema. The model picks a report id + params, never SQL.
2. `run_report` tool (`kind: "read"`) in the shared registry — available over MCP per Decision 6 (it's a read tool).
3. Panel renders the result as a structured table with CSV/PDF export, plus a `ui` directive "Open in Reports" pointed at the existing `/reports` route.
4. Gate behind the capability flag.

**Acceptance:** `run_report` returns correct data for at least 2 report types against real warehouse data. Export works. "Open in Reports" navigates correctly. An MCP client can call `run_report` directly.

## Phase 3 — Voice (push-to-talk + optional TTS — hands-free explicitly excluded, Decision 5)

1. New `src/features/copilot/voice.ts`: press-and-hold mic handler using the Web Speech API where available; fallback records audio and calls a new gateway STT edge function for handhelds/iOS.
2. Transcript always lands in the composer for review — never auto-sent. No continuous listening, no wake phrase — that's a separate later phase, not this one.
3. Optional TTS output (off by default), short-answer mode when voice is on.
4. Pass warehouse vocabulary hints (SKU/location/client terms) to the STT call.
5. Gate behind the capability flag.

**Acceptance:** press-and-hold mic produces an editable transcript on both a Web-Speech-capable browser and a device forced onto the STT fallback. TTS toggle works and defaults off. Confirm no code path enables always-on listening in this phase.

## Phase 4 — File ingestion

1. New `supabase/functions/copilot-ingest/index.ts` (Decision 3 — new code, same AI-gateway call pattern as `container-vision`, not a call into it). Routes: container-front photos → the existing `container-vision` path for that sub-case; packing-list/PO/invoice PDFs/images → new typed line-item extraction; CSV/XLSX → parsed rows for Phase 5.
2. New private `copilot-uploads` storage bucket, owner-scoped policies (mirror the existing `imports` bucket pattern in `reports-core.ts`).
3. Extraction always produces a draft with per-field confidence; below-threshold fields flagged for review. Reply shows a diff-style preview with "Open in Receiving" / "Create import" / "Discard" actions.
4. Chat panel gets attach + camera controls.
5. Decide the ingestion-draft table shape now (bespoke, per Decision 2 — either its own table or reuse `copilot_import_drafts` if the shape genuinely fits; don't default to the old `copilot_suggestions` table).
6. Gate behind the capability flag.

**Acceptance:** uploading a packing-list image produces a reviewable line-item draft with confidence flags. A container-front photo still resolves via the existing ISO 6346 path, unchanged. Nothing writes to a live table without the explicit action click. Injection test: embed an instruction-like string in a test document's text and confirm the model does not act on it — only extracts it as inert field data.

## Phase 5 — Gated import pipeline

1. **Additive migration:** `copilot_import_drafts`, `copilot_import_mappings`, `copilot_approvals` (Decision 2 — bespoke, not `copilot_suggestions`), with grants + RLS.
2. `create_draft_import` / `validate_import` / `commit_import` tools (`kind: "draft"` for the first two; `commit_import` requires the approval token) — new, independent logic per Decision 4, not calling into `reports-core.ts`.
3. `commit_import` refuses without a valid single-use, short-lived approval token bound to draft id + user, minted only by the UI's Approve click. Writes through the existing admin upsert path, logs an audit event, returns created-vs-updated counts.
4. Remember import mappings per client/file-shape for repeat-file auto-mapping.
5. Confirm draft-kind tools stay excluded from the MCP catalog (Decision 6) — chat-panel only.
6. Gate behind the capability flag.

**Acceptance:** a CSV import proposed via chat requires an explicit in-app approval click before any live-table write. A second upload of the same file shape reuses the remembered mapping. An MCP client cannot call `create_draft_import` (absent from its catalog). Full audit trail present in `copilot_tool_calls` + `copilot_approvals`.
